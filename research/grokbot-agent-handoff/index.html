How Grokbot can pass a coding job to another agent

For GrokChief (Grok-based) handing work to gptdev (GPT/Codex) or a Claude-based agent — on a small self-hosted team with Gitea and an AWS deploy. The short answer is not a protocol. It’s a file, a branch, and an Issue.

Nov 11, 2026Gitea + AWS host + private boardNo native Grok → GPT/Claude handoff existsSources linked for every confirmed claim

VerdictWhat Grok offersStandardsPractical methodPlanOpen questions

Bottom line

There is no out-of-the-box Grok → GPT/Claude handoff. Every workable route is either (a) a shared artefact both agents can read/write — repo, branch, task file, Issue — or (b) a wrapper/framework you build around both agents. Start with (a). Do not start with A2A.

Do now — Option 1

Git + Issue + handoff file

Branch + tasks/active/*.md + Gitea Issue/PR + AGENTS.md. Works today, no new services, no vendor lock-in.

Do next — Option 2

Shared Gitea MCP server

Same handoff, but machine-readable: both agents create Issues, branches and PRs through the same MCP tools.

Later — Option 3

A2A or one orchestrator SDK

Future-proof, highest effort. Requires wrapping Grok — xAI has no confirmed native A2A support.

The distinction that prevents wasted work

Three protocols, three different jobs

Confusing these is the most common dead end. Only one of them is actually agent → agent.

2 — Standards in detail

How each protocol would work, mechanically

A2A — the actual agent → agent standard

  1. Discovery: remote agent publishes an Agent Card (JSON) at /.well-known/agent-card.json — identity, skills, endpoint, auth. v1.0 adds signed cards (JWS).
  2. Send: JSON-RPC 2.0 message/send over HTTPS (v1.0 also binds gRPC and HTTP+JSON/REST), auth per the card (OAuth 2.0, bearer, API key, mTLS).
  3. Work: remote opens a Task — submitted → working → input-required / completed / failed / cancelled / rejected — and runs opaquely; the caller sees nothing of its internals.
  4. Return: poll tasks/get, stream via SSE, or webhook push; completion returns Artifacts (files, structured data, text).

Both sides must: be (or be wrapped as) an A2A server/client — HTTPS endpoint, agent card, JSON-RPC methods, task lifecycle, advertised auth. In practice: an SDK/framework (Google ADK, LangGraph, CrewAI, Semantic Kernel, Mastra, or the a2aproject/A2A SDKs). Maturity: announced by Google 2025-04-09 with 50+ partners; donated to the Linux Foundation June 2025; v1.0.0 is the latest released version on the spec site (secondary sources date it 2026-03-12 and April 2026 — version is settled, exact date is not); native in Azure AI Foundry, Copilot Studio, Bedrock AgentCore, Google Cloud — but most use outside those platforms is still PoC-level per analysts.

MCP — agent → tools

Host (Grok Build / Claude Code / Codex) → Client (one connection per server) → Server exposing tools (model-controlled), resources (app-controlled context) and prompts (user-controlled templates). JSON-RPC 2.0 over stdio (local) or Streamable HTTP (remote); the 2026-07-28 revision made the core stateless. Mature, de-facto standard. Security note from the spec: treat tool descriptions / server instructions as untrusted unless the server is trusted; require consent for write actions — relevant for a write-capable Gitea MCP server.

ACP — host → agent

Created by Zed Industries (Aug 2025), co-developed with JetBrains from Oct 2025; registry launched Jan 2026. Flow: initialize → authenticate → session/new → session/prompt ↔ session/update. Stable wire protocol is v1; v2 is draft. Local transport is stdio only — remote HTTP/WebSocket is an RFD / work in progress, not normative. Grok Build is native (grok agent stdio); Claude Code and Codex connect via adapters (codex-acp for Codex). Useful as an orchestration surface for a human or script — not an agent → agent channel.

OpenAI Agents SDK handoffs & same-vendor subagents

SDK: handoffs=[billing_agent, refund_agent] (or handoff() with on_handoff, input_type, input_filter) injects a transfer_to_<name> tool; the Runner switches the active agent and by default passes full history. Agent.as_tool() is the manager-pattern alternative where control returns to the caller. Handoffs stay within a single run; both agents must be Agent objects in the same program. Claude Code subagents (Agent tool, formerly Task; .claude/agents/ Markdown + YAML; built-ins Explore / Plan / general-purpose; one level deep by default) and Codex subagents (roles default / worker / explorer; TOML in .codex/agents/; codex exec for scripted runs) are likewise same-session only. Unverified: the Responses API multi-agent beta (multi_agent.enabled, spawn_agent etc., default 3 concurrent) is secondary-only in this run.

Sources: Claude Code subagents — code.claude.com/docs/en/sub-Agents · Codex subagents (secondary summary) — docs.arantic.com/codex/subagents · ACP remote transport RFD — agentclientprotocol.com/rfds/streamable-http-websocket-transport

3 — What works between any two agents

The practical method: the handoff is a file, not a chat message

Chat history does not transfer between vendors. A Markdown file in the repo does. Git is the one interface every coding agent already has — the diff is the context.

1 · BranchGrokChief works on agent/grokchief-<slug>, never on main. Pushes.
2 · Task fileWrites tasks/active/<date>-<slug>.md with the full payload below.
3 · IssueOpens a Gitea Issue: owner = receiver, label ready-for-gptdev, links branch + file.
4 · AnnouncePosts on the board: Issue #, branch. Chat announces — the repo holds the truth.
5 · Work & PRReceiver checks out the branch, works, validates, sets ready-for-review, opens PR.
6 · Human mergesReview in Gitea; merge to main; deploy to AWS only from main.

Shared board = Gitea Issues

One Issue per task. Labels: handoff, ready-for-gptdev / ready-for-claude, in-progress, needs-review, blocked. Assignee = agent name. Comments = running log. Receiver polls open Issues with its label (git / Gitea API, or MCP in Option 2) and claims by commenting / moving the label.

Limitation: Gitea has no “assign to an AI and wake it.” The receiver must be running — a cron/headless loop or an operator starting it — and polling. Labels are convention, not enforcement.

AGENTS.md — the shared contract

A short root AGENTS.md every agent reads on entry: project overview, exact install/test/lint/build commands, conventions, boundaries (never edit .env, never deploy to prod), git/PR workflow, and the handoff protocol. Grok Build, Codex, Cursor, Gemini CLI, Aider and OpenCode read AGENTS.md; Claude Code reads CLAUDE.md — add one line, @AGENTS.md, as a pointer. Keep it short; route to detail files.

Status strings (use literally, so grep/scripts can find work): Planner → Coder creates the task file; Coder → Reviewer sets status: ready-for-review; Reviewer → Planner sets approved or needs-revision with specific feedback.

Minimum information — enforce this checklist

  • ✓Goal — one sentence, the outcome. Without it the receiver optimises for the wrong thing.
  • ✓Context / why — decisions, Issue/PR links, what was already tried or ruled out.
  • ✓Scope — files/functions in play and out of scope.
  • ✓Starting point — branch name + base commit SHA. “Latest main” is ambiguous.
  • ✓Match example — a file that already does it right; the cheapest quality lever.
  • ✓Constraints — stack, versions, style, boundaries (no secrets, no prod, no .env).
  • ✓Tests / validation — exact commands and how to run them.
  • ✓Acceptance criteria — testable “done when”, not “make it better”.
  • ✓Evidence expected back — files changed, commands + results, checks not run + reason, assumptions, risks.
  • ✓Owner + status + next action (+ deadline/priority if any).

Handoff template — commit as tasks/TEMPLATE.md

# Handoff: <title>
Goal: [one sentence, the outcome — not the method]
Scope: [exact files / functions / endpoints in play]
Out of scope: [what NOT to touch]
Approach: [pattern, limits, logging, conventions to follow]
Match: [path/to/a/file that does it right]
Context: [why this exists, links to Issue/PR, relevant decisions]
Branch: [branch name, base commit SHA]
Done when / Acceptance criteria: [tests passing, commands to run, human reviews diff]
Evidence on completion: [files changed, validation commands + results,
  checks NOT run + reason, assumptions, risks, follow-up]
Status: [todo | in-progress | ready-for-review | approved | needs-revision]
Owner: [agent name, e.g. gptdev]  |  Previous owner: [e.g. GrokChief]

Copy template

Template sources (community practice, no single official standard): sublimecoding.com/blog/coding-agent-rollout-engineering-team · thepromptshelf.dev/blog/writing-effective-agentsmd-guide · codeharness.kuckit.dev/agents-md-template · Gitea workflow: voodoo.business/blog/2026/11/05/using-your-self-hosted-gitea-server

Rule for the board/chat: chat is the notification layer only — announce, clarify, report completion. It is ephemeral and unversioned; a fresh agent session can’t read it as state. Never put the only copy of a task in chat. Chat announces, the repo holds the truth.

4 — Recommendation for this team

Ranked plan: practicality first

A handoff that depends on a protocol neither agent natively speaks will not happen. A handoff that is a file + a branch will.

Option 1 · Recommended first

Git + Gitea Issue/PR + file handoff

tasks/ + AGENTS.md. Highest practicality — works today, no new services, no new protocol, no lock-in.

01
  1. Add a root AGENTS.md (project, exact test/build/deploy commands, boundaries, “work on a branch, human merges”, handoff protocol + tasks/ convention). Add one-line CLAUDE.md (@AGENTS.md).
  2. Add tasks/active/ and tasks/done/; commit the template as tasks/TEMPLATE.md.
  3. Fix conventions in AGENTS.md: branch agent/<agent>-<slug> (e.g. grokchief/add-login); labels handoff, ready-for-gptdev / ready-for-claude, in-progress, ready-for-review, blocked; status strings todo / in-progress / ready-for-review / approved / needs-revision.
  4. GrokChief handoff procedure (in AGENTS.md): finish on its branch → push → write tasks/active/<date>-<slug>.md → open/update Issue (owner = receiver, label ready-for-<agent>, link branch + file) → announce on the board with Issue # + branch.
  5. Receiver intake (in AGENTS.md): read AGENTS.md → list open Issues labelled ready-for-<name> → read task file → git fetch && git checkout <branch> (or branch off it) → work → run validation → update task file (evidence + ready-for-review) → push → open/update PR → comment on Issue → announce.
  6. Run unattended legs headless: Grok Build grok -p "<prompt>" (verified live); Codex codex exec "<prompt>" (secondary source) — or an operator starts each agent with the Issue/task-file path as its prompt. Human merges to main; deploy to AWS only from main, existing path unchanged.

Limitations: async only (no wake-up without a poller or human); no live progress streaming; relies on agents following the written convention — keep the template + AGENTS.md short and checkable; merge conflicts if two agents touch the same files (mitigate: worktrees / one branch per task); no context transfer beyond what’s written in the file — by design, and also its strength.

Option 2 · Next

Shared MCP server for Gitea (+ board)

Medium-high practicality. Builds on Option 1; makes the handoff machine-readable so agents act on Gitea without leaving their CLI. Do after Option 1 works.

02
  1. Run a self-hosted Gitea MCP server on the Gitea host/network (stdio locally, or Streamable HTTP on your private network behind auth). Either write a small Python/TS server against the Gitea REST API (tools: list_issues, create_issue, create_branch, create_pull_request, get_pull_request, merge_pull_request, dispatch_workflow), or evaluate a third-party integration — e.g. Composio’s Gitea MCP for Codex (Create Branch / PR, Get PR, Merge PR, Dispatch Workflow, Get Commit; third-party, not official Gitea — check auth/pricing first).
  2. Give both agents the same server. Grok Build: grok mcp add --transport http gitea https://<internal-host>/mcp --header "Authorization: Bearer ${GITEA_TOKEN}", or project-scoped in .grok/config.toml. Claude/Codex: same server in their MCP config — one project .mcp.json can serve several agents (Grok Build reads it too). Start read-only; add write tools behind an allowlist once trusted.
  3. Keep Option 1’s file + Issue as the source of truth. MCP is the action layer, not a replacement for the written handoff.
  4. Add a Gitea Actions workflow (.gitea/workflows/) running tests on every PR, so incoming work is checked automatically before human merge.

Limitations: you host, secure and maintain the server (auth, token scoping, allowlist — a write-capable MCP server is powerful; a compromised/prompt-injected agent could create/merge PRs). No official Gitea MCP server was verified in this run — integrations are third-party or DIY, so budget maintenance. Remote MCP from the xAI API needs a publicly reachable Streamable HTTP/SSE endpoint (no stdio); the Grok Build CLI can use local stdio. MCP still doesn’t notify the receiver — keep Option 1’s announcement/polling.

Source: composio.dev/toolkits/gitea/framework/codex (third-party)

Option 3 · Later / experimental

A2A — or rebuild both agents in one orchestrator SDK

Lowest practicality today for a small self-hosted team; highest long-term interoperability. Do not start here.

03

A2A route:

  1. Wrap each agent as an A2A server: a small Python/TS service (A2A SDKs from a2aproject/A2A, or Google ADK / LangGraph / Mastra) exposing /.well-known/agent-card.json (skills e.g. implement-task), message/send, tasks/get, SSE streaming, returning Artifacts. The wrapper translates A2A task → prompt + branch + task file for grok -p / codex exec / claude -p, runs it, and translates the diff/PR back into an Artifact.
  2. Host both wrappers on your private network / AWS host behind HTTPS + auth (OAuth 2.0 / API key / mTLS per the card). Each wrapper also acts as A2A client to the other.
  3. Keep Option 1 underneath: the A2A payload is the §3 checklist handoff; the Artifact is the branch/PR reference + evidence. A2A is the envelope, git is still the payload.

Alternative orchestrator route: rebuild both agents as Agent objects in one OpenAI Agents SDK (or LangGraph/CrewAI) program with native handoffs=[...] — in-process handoffs with tracing/guardrails, but you lose the Grok Build / Codex / Claude Code CLIs and re-implement their tool loops.

Limitations: no native Grok A2A (§1) — you build and maintain both wrappers; A2A adoption outside enterprise platforms is still PoC-level; auth, lifecycle, retries, timeouts and hours-long coding tasks are all your problem; debugging spans two services + two CLIs + git. Worth it only when handoffs are frequent, multi-hop, or need machine-readable discovery/routing a board + labels can’t express.

What not to do: don’t try to make Grok Build, Claude Code or Codex subagents hand off to each other (same-vendor, same-process only). Don’t treat ACP as agent → agent (it’s host → agent). Don’t treat MCP as a handoff (it’s a shared tool layer).
